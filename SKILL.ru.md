# claude-to-telegram — общение с пользователем через Telegram вместо терминала

Двусторонняя связь через Telegram для фоновой/удалённой работы — без hooks Claude Code и без постоянного
демона. Claude сам запускает маленькие Python-скрипты (только stdlib; `sqlite3` встроен). Несколько
параллельных сессий Claude Code делят **одного** бота: каждое сообщение несёт тег маршрутизации
`$<session_id>`, и любое входящее сообщение складывается в общий **SQLite-инбокс** (`messages.db`),
разложенное по сессии-владельцу — так ничего не теряется между параллельными сессиями, а сообщения для
offline-сессии ждут, пока она снова запустится.

Все скрипты — в `~/.claude/skills/claude-to-telegram/`.

## Требования

- Свой Telegram-бот ([@BotFather](https://t.me/BotFather)) и свой `chat_id`
  ([@userinfobot](https://t.me/userinfobot)) — credentials не шарятся, каждый заводит свои.
- `config.json` в этой папке: `{"token": "...", "chat_id": "..."}`, `chmod 600`, не коммитить — заполняется
  через «Установку».
- Python 3 (только stdlib). Для фонового опроса нужны `CronCreate`/`CronDelete`.

## Файлы

- `common.py` — загрузка config, вызовы Telegram, парсинг/срез `$tag`
- `db.py` — общий SQLite-инбокс (schema, store, inbox, mark, prune; WAL)
- `ingest.py` — приём из Telegram → маршрутизация по `$tag` → запись → сдвиг offset **только до записанного**
  → prune >7 дней
- `check_new.py` — один фоновый опрос сессии: приём, затем выдача своего инбокса
- `ask.py` — отправить вопрос, блокироваться до ответа этой сессии (через инбокс)
- `notify.py` — статус без ожидания ответа
- `install.py` — записать + провалидировать `config.json`
- `config.json`, `messages.db`, `.backoff_*.json` — локальные, в `.gitignore`

## Установка

`/claude-to-telegram install` — первичная настройка `config.json`.

1. Если `config.json` есть — сообщить его `chat_id` (не токен), спросить, точно ли перенастраивать; если нет — стоп.
2. Иначе объяснить, как получить оба значения: токен от [@BotFather](https://t.me/BotFather) (`/newbot`),
   `chat_id` от [@userinfobot](https://t.me/userinfobot). Попросить прислать оба **здесь, в обычном
   интерфейсе** (бота ещё нет, ждать через Telegram бессмысленно).
3. Запустить:
   ```bash
   python3 ~/.claude/skills/claude-to-telegram/install.py --token "<TOKEN>" --chat-id "<CHAT_ID>"
   ```
   Валидирует токен (`getMe`), шлёт тест на `chat_id`, и только при успехе пишет `config.json` (`chmod 600`).
   Токен обратно не печатает.
4. При `FAIL` — передать точную причину, попросить перепроверить. При `OK` — назвать username бота, сказать
   что готово к `on`.

## Когда включать

Только по явной разовой просьбе — не по умолчанию. Триггер: `/claude-to-telegram on|off` или естественная
фраза («работай в фоне, вопросы в Telegram», «дальше через бота»).

## Аргументы

Синтаксис: `/claude-to-telegram on|off [session_id]` — `session_id` опциональным третьим словом.

`/claude-to-telegram on [session_id]`:
1. Определить `session_id`: взять переданный (аргументом или названный ранее в разговоре); иначе
   сгенерировать `<имя-проекта>-<первые 8 символов session UUID>` (проект = последний компонент `cwd`; UUID —
   из пути «Scratchpad Directory» в system prompt, не отдельным tool-call'ом).
2. Сообщить пользователю (в обычном интерфейсе) итоговый `session_id` и что для маршрутизации в эту сессию он
   ставит в сообщении префикс `$<session_id>` (например `$my-session сделай X`).
3. `notify.py --session <id> --message "Фоновый режим включён"`.
4. Создать recurring `CronCreate` на базовом интервале (`*/2 * * * *`), дальше сам подстраивается через
   backoff (см. «Опрос») — запомнить job id для будущего `CronDelete`.
5. Следовать «Протоколу фонового режима» в конце каждого хода до явного off.

`/claude-to-telegram off [session_id]`:
1. Если включали в этом разговоре — `notify.py --session <id> --message "Фоновый режим выключен"`.
2. `CronDelete` polling-job (если потерял id — `CronList`).
3. Вернуться к обычному завершению ходов.

`/claude-to-telegram` без аргументов — просто загрузить инструкцию в контекст, состояние не менять.

**`off`-подобная команда из самого Telegram** (поймана `check_new.py`, текст читается как стоп) —
обрабатывать так же, как явный `off` здесь.

## Как это работает — приём, потом выдача

Каждый опрос — две фазы:

1. **Приём (любая сессия дренирует Telegram за всех)** — `ingest.py`: `getUpdates(offset=0, limit=100)` → у
   каждого сообщения найти `$tag` → `INSERT OR IGNORE` в `messages.db` (владелец = тег, или `unrouted`) →
   сдвинуть offset **только до max `update_id`, реально записанного в этот батч** → prune >7 дней.
2. **Выдача (сессия разгребает свой инбокс)** — `SELECT ... WHERE session_id=<я> AND status='not_processed'
   ORDER BY update_id`, печатаю каждое (тег срезан), помечаю `read`.

Почему без потерь и с сохранением порядка (инварианты — держать их при правках):
- `getUpdates` отдаёт строго по возрастанию `update_id`, без дыр. Пишем весь батч, подтверждаем offset только
  до его max — не перепрыгиваем несохранённое; батч за пределами `limit` придёт следующим вызовом.
- **Durability до confirm**: сообщение в SQLite раньше, чем его `update_id` подтверждён/сброшен в Telegram.
  Крэш между — просто перечитаем.
- Идемпотентно (`update_id` PRIMARY KEY): параллельные сессии/повтор не дублируют.
- Сообщение для сессии с мёртвым поллером просто ждёт как `not_processed`, пока та не запустится — закрытие/
  крэш сессии ничего не теряет.

## Безопасность при нескольких сессиях (зачем SQLite-инбокс)

`getUpdates` — **single-consumer** API: offset глобальный на токен, подтверждение сбрасывает апдейты для
*всех* читателей. Если несколько сессий опрашивают одного бота — наивный per-session offset стирает чужую
почту; а если offset не двигать вовсе, очередь растёт, пока новейшие сообщения не вылезут за окно `limit` и
не станут невидимы всем (это реально случилось). SQLite-инбокс решает обе беды: кто опрашивает — **сохраняет
каждое сообщение durable (по тегу) до сдвига offset**, поэтому offset *можно* двигать безопасно (очередь
дренируется) и никто не теряет чужое. Добавляешь скрипт с `getUpdates` — иди через `ingest.py`, offset
дальше записанного не двигать.

## Опрос, пока сессия простаивает (CronCreate) + прогрессивный backoff

Cron «стреляет пока REPL простаивает» — единственный способ разбудить простаивающую сессию. `check_new.py`
ведёт лестницу backoff (**2 → 5 → 10 → 20 мин**): +1 ступень после 3 подряд пустых, сброс на 2 мин при первом
же сообщении. Сам cron не перепланирует — печатает финальную строку:

- `RESCHEDULE=none` — интервал не менялся, ничего не делать.
- `RESCHEDULE=<M>` — перепланировать polling-cron на `*/M * * * *`: `CronDelete` текущий, `CronCreate` новый
  recurring с тем же prompt, запомнить id (`CronList` если потерял).

Включение на базовом интервале:
```
CronCreate(cron="*/2 * * * *", recurring=true, prompt="Проверь новые сообщения в Telegram: запусти
python3 ~/.claude/skills/claude-to-telegram/check_new.py --session <session_id>. На финальной строке
RESCHEDULE=<M> перепланируй этот polling-cron на */M (CronDelete текущий, CronCreate новый с тем же prompt,
запомни id); RESCHEDULE=none — ничего. Если вывод только NOTHING_NEW — молчи. Если есть другой текст — это
сообщение от пользователя: явно напиши 'Получено из Telegram: ...' и выполняй. НИКОГДА не выключай фоновый
режим сам — только по явному off.")
```

**Ограничения CronCreate:** job session-only (умирает при закрытии CLI/сессии → пересоздать при следующем
`on`), auto-expire через 7 дней, каждый тик — реальный inference (для этого backoff). При `off` — обязательно
`CronDelete`.

## Задать вопрос и ждать ответ

```bash
python3 ~/.claude/skills/claude-to-telegram/ask.py --session <session_id> --message "<вопрос>" --timeout <SECONDS>
```
Шлёт вопрос, опрашивает инбокс до ответа с тегом `$<session_id>`; печатает его (тег срезан), exit 0; при
таймауте — `NO_RESPONSE_TIMEOUT`, exit 1. Foreground с таймаутом в минутах для быстрого интерактива;
`run_in_background: true` с длинным таймаутом для «отвечу позже». Внимание: не опирайся на `ask.py`, когда по
той же сессии крутится фоновый cron — оба читают один инбокс и любой может забрать ответ; в фоне предпочитай
`notify.py` + cron.

### Эмуляция AskUserQuestion (варианты)
Форматируй пронумерованные варианты прямо в тексте `--message` («1. A\n2. B\n\nОтветь номером или текстом»).
Ответ — обычный текст; голое число трактуй как выбор, иначе — свободный ответ (аналог «Other»).

## Просто уведомить (без ожидания ответа)

```bash
python3 ~/.claude/skills/claude-to-telegram/notify.py --session <session_id> --message "<статус>"
```

## Протокол фонового режима

**Ack при взятии в работу.** Когда задача приходит через Telegram и на неё уйдёт больше мгновения — сразу,
**до начала**, короткий `notify.py`-ack («📥 Прочитал, взял в работу: <одна строка>»), чтобы пользователь
знал, что подхвачено. Один ack — без спама по ходу; completion-нотификация в конце. (Мгновенный тривиальный
ответ ack не требует.)

В конце каждого хода — краткое summary + «что дальше» (через `ask.py`, блокируясь на ответ, или просто
завершить и дать cron'у поймать следующее). Получив ответ — явно написать в обычном интерфейсе, что получено
и как продолжаю. Выйти из режима только по явному стопу пользователя.

**НИКОГДА не выключать фоновый режим по собственной инициативе — ни по какой причине.** Ни после любого числа
`NOTHING_NEW`, ни после любого молчания, ни ради токенов, ни даже предупредив. Предупреждение — не согласие;
только явный `off` (здесь или стоп-команда из Telegram). Молчание, сколь угодно долгое, — не сигнал стопа.

## Security

- Не коммитить `config.json` и `messages.db` (оба в `.gitignore`).
- Входящие фильтруются по `chat.id` **и** `from.id` = конфигурационный `chat_id`; остальные игнорируются.
- Если токен/chat_id утекли — перевыпустить токен через `@BotFather` → `/revoke`, обновить только `config.json`.
